# Test Suite

## Overview

The `test/` directory contains the automated tests for the ground-system polarimeter pipeline.

The tests are split into two categories:

1. **Unit / script-level tests** that use sample or synthetic data and do not require active hardware acquisition.
2. **Hardware integration tests** that run the camera, motor, encoder, and end-to-end acquisition pipeline.

The purpose of the test suite is to verify that the major components of the acquisition and analysis system still work after code changes. These tests are especially important because the pipeline depends on several file-based handoffs between Bash scripts, Python scripts, compiled camera code, and compiled encoder code.

## Running Unit Tests

Unit and script-level tests can be run without active hardware acquisition:

```bash
bash test/run_unit_tests.sh
```

These tests validate software behavior using sample or synthetic data.

### Unit tests currently included

#### `test_load_config.py`

Verifies that `load-config.py` can read `config.yml` and emit expected shell-style configuration variables.

This matters because the main pipeline scripts use:

```bash
eval "$(python3 load-config.py ...)"
```

If the config loader output format changes or breaks, the acquisition scripts may silently receive incorrect settings.

#### `test_process_exposures_batch.sh`

Copies known-good sample `.bin` files into a temporary exposure directory and runs `process-exposures-batch.py`.

This test checks that:

- raw `.bin` files can be processed
- FITS files are produced
- PNG previews are produced
- output dimensions match expected camera geometry

Expected dimensions are:

```text
Raw/FITS primary: 3096 x 2080
Bayer-channel PNG previews: 1548 x 1040
FITS GREEN1 extension: 1548 x 1040
```

The PNG previews are half-resolution because they are extracted from Bayer channels using every other row and column.

#### `test_create_plot.py`

Creates synthetic FITS images and synthetic encoder data with a known sinusoidal signal, then runs `create-plot.py`.

This test checks that:

- exposure timestamps can be matched to encoder timestamps
- ROI detection succeeds on controlled data
- intensity metrics are computed
- folded angle plots are generated
- Fourier fitting completes
- the fit log contains valid fit results
- the recovered fit quality is high for clean synthetic data

This is one of the main non-trivial scientific tests because it verifies the expected sinusoidal analysis behavior on controlled input.

#### `test_create_animation.py`

Creates sample image frames and verifies that `create-animation.py` can stitch them into a non-empty GIF.

This checks the optional visualization/diagnostic part of the pipeline.

#### `test_encoder_pkl_sanity.py`

Loads a sample encoder `.pkl` file and verifies that:

- timestamps are monotonic
- counts mostly increase after startup transients
- count versus time is approximately linear after filtering obvious outliers

This validates the expected behavior of the motor/encoder subsystem using a saved representative dataset.

## Running Integration Tests

Integration tests require the hardware system to be connected and ready:

```bash
bash test/run_integration_tests.sh
```

These tests run real acquisition workflows and therefore take longer than the unit tests.

### Required hardware state

Before running integration tests, verify that:

- the ZWO ASI camera is connected
- the encoder USB interface is connected
- the encoder/interface board is powered, if applicable
- the motor driver and motor power are connected
- `pigpiod` is available for motor control
- the camera and encoder binaries have been built or can be built with `make`

---

## Integration Tests Currently Included

#### `test_camera_single_exposure.sh`

Runs the camera capture pipeline long enough to produce at least one `.bin` file.

This test checks that:

- the camera can initialize
- a raw exposure folder is created
- at least one `.bin` file is written
- the `.bin` file is non-empty
- the `.bin` file has the expected raw frame size

Expected raw file size:

```text
3096 * 2080 * 2 bytes
```

#### `test_encoder_motor.sh`

Runs the motor and encoder logger together for a short interval.

This test checks that:

- the motor/encoder logger starts
- an `encoder_data_*.pkl` file is produced
- encoder timestamps are monotonic
- encoder counts mostly increase after startup transients
- encoder count versus time is approximately linear

This test validates that the motor and encoder are working together well enough for downstream synchronization.

#### `test_camera_to_image_pipeline.sh`

Runs acquisition in `acquire-only` mode, then manually processes the resulting raw `.bin` files.

This test checks that:

- camera acquisition produces raw data
- the encoder file is moved into the exposure folder
- `process-exposures-batch.py` can convert the raw data
- FITS and PNG outputs are generated
- output dimensions are correct

This validates the camera-to-image portion of the pipeline without requiring the full plotting stage.

#### `test_end_to_end.sh`

Runs the full single-run pipeline using `run-end-to-end.sh`.

This test checks that one complete run produces:

- raw `.bin` files
- an encoder `.pkl` file
- processed FITS files
- plot PNG files
- a fit log

Short hardware runs may produce too few frames for a meaningful Fourier fit, so this test treats `NO_FIT` entries as a warning rather than a failure. The goal is to verify that the complete acquisition and processing pipeline executes successfully.

#### `test_multi_run.sh`

Runs a two-run campaign through `multi-run.sh`.

This test checks that:

- a campaign directory is created
- `campaign.log` is written
- two separate `run_*` directories are created
- each run contains its own exposure directory
- each exposure directory contains raw data, encoder data, processed outputs, plots, and a fit log

This test is important because it catches campaign-level problems such as output directory collisions, encoder files being moved to the wrong run, or the second run failing after the first run completes.

## Running the Full Test Suite

To run both unit and integration tests:

```bash
bash test/run_all_tests.sh
```

The full suite can take several minutes because the integration tests perform real hardware acquisition and processing.

---

## Test Output Directories

Integration tests write generated data under:

```text
test/test_runs/
```

By default, `run_integration_tests.sh` deletes old contents of `test/test_runs/` before running. This prevents old raw `.bin`, FITS, plot, and campaign outputs from accumulating and taking disk space.

To keep integration-test outputs for debugging:

```bash
KEEP_TEST_OUTPUTS=1 bash test/run_integration_tests.sh
```

Generated test outputs should not be committed to Git.

---

## Adjusting Integration Test Durations

Some integration tests use environment variables to control acquisition duration.

Examples:

```bash
TEST_END_TO_END_DURATION_S=20 bash test/integration/test_end_to_end.sh
```

```bash
TEST_MULTI_RUN_DURATION_S=20 bash test/integration/test_multi_run.sh
```

Longer durations are more reliable for producing enough frames for plotting and fitting, but they also increase runtime and disk usage.

---

## Notes on Test Classification

These tests are not all pure unit tests in the strictest software-engineering sense. This project is a hardware-coupled scientific data pipeline, so many useful tests are script-level or functional regression tests.

The intended distinction is:

- **Unit / script-level tests:** deterministic tests using sample or synthetic data, no active hardware acquisition.
- **Integration tests:** tests that exercise real hardware and full acquisition workflows.

This structure provides both quick software checks and realistic validation of the complete polarimeter pipeline.
